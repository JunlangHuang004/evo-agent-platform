# 交接卡开发计划

Task 1 结束后形成一份交接文档，发到本群，并让同一团队的 Task 2 规划者读到。每个 Agent 只看见自己在 Task 1 里的经验。

## 为什么这样分

`Mid_Test(1)` 里三组第二题都接着同一群做，但接着用的东西不一样：

| 场景 | Task 2 必须沿用的 | 不要当成新题目正文的 |
| --- | --- | --- |
| 软件：预订系统 → 用量看板 | 已发布的系统和其中的预订记录 | 另造一份假数据 |
| 新闻：校园报道 → 检测器核查 | 编辑室已经确认的读者、口径 | 把第一篇报道的每个文件都当成核查对象 |
| 基金：客户方案 → 半导体简报 | 已确认的客户约束和风险口径 | 把投资方案直接改写成行业幻灯片 |

练习题也是同一关系：设备台账的看板必须用上一题的借还记录；事实核查幻灯片必须保持简报里的来源和未定结论。

所以交接文档是给规划者的团队摘要，不是把所有人的私有经验合成一份指令。个人成败仍按「同一团队、同一个 Agent」保留。

## 什么时候写

群聊里的任务运行进入结束状态就写。`done` 和带有已发布文件的 `partial` 都写。完全没有发布文件的 `failed` 也写一张短卡，标明没有可继承的产物。

只等「成功结束」会漏掉实际最常见的情况：第一题部分完成，第二题仍然要接着用已经发布的文件和已知缺口。

重置对话只清屏幕上的消息。交接卡存在该团队自己的数据里，不随重置消失。

## 交接卡里写什么

由程序根据账本生成，不另叫一次模型，避免总结编造结果。篇幅限制在约 2000 字。

1. 上一题原文目标、运行编号、结束状态。
2. 已发布文件：路径、所有者、SHA256、是否只读。要修改必须发布新版本。
3. 尚未关闭的验收缺口和错误码。
4. 沿用规则，按产物形态选一句：有可运行入口时写「下一题使用这些记录，不要另造数据」；主要是文章或研究时写「沿用来源、范围和未定结论；旧文件不是新题目的正文」。
5. 成员索引：每个参与者一行，只写子任务标题、状态、错误码。不写该成员的详细教训。

卡片发到群聊，发送者记为系统。同时存成结构化记录，供下次规划读取。

## 谁在 Task 2 读到什么

规划者在拆 Task 2 时，用户上下文里增加 `handoff`。内容就是上面这张卡，外加他本人的经验条目。他已经能看见本次勾选成员的编号、名字、能力标签和身份说明；交接卡不重复这些，也不包含工具名单。

其他 Agent 开始自己的子任务时，只附加「同一团队、同一个 Agent」的 Task 1 经验：失败观察或成功记录、关联的调用编号。不把别人的经验放进他的提示。这些条目标明是历史事实，不是必须执行的指令。

跨团队不读。私聊不产生这张群交接卡。

## 改哪些地方

| 位置 | 改动 |
| --- | --- |
| `backend/engine.py` 运行收尾 | 群任务进入终态后生成交接卡，写入群消息和团队存储。 |
| `backend/engine.py` `_plan` | 把本团队最近一张交接卡放进 `planning_context['handoff']`。重置后仍能读到。 |
| `backend/engine.py` 子任务开工 | 只注入该 Agent 自己的上一题经验。 |
| `backend/persistence.py` | 按团队保存最近一张交接卡，不放进别的团队目录。 |
| 测试 | 覆盖下面四条，不调用真实模型。 |

## 验收

1. 软件第一题以 `partial` 结束并发布了页面文件。第二题规划上下文含这些文件的哈希，以及「使用已有记录、不要另造数据」。
2. 新闻第一题发布了报道。第二题交接卡写明沿用来源和未定结论，不把旧稿标成新核查文章。
3. 重置群聊后再发第二题，规划者仍能读到交接卡。
4. 开发者的失败经验只出现在开发者的后续提示里，不出现在测试工程师的提示里，也不出现在另一个团队的规划里。
