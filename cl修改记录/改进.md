# 平台技术改进方案（面向 Mid-Test 类任务与期末展示）

本文档针对 R13 六题复测暴露的具体问题与课程 `requirements.md` 评分点，列出可以在代码层落地的改进。每一项都给出：**问题现象 → 改在哪里 → 怎么改 → 验收标准**。

**适用场景**：期末展示老师会给"类似 Mid-Test 的新任务"，不能预先知道题目。因此所有改进必须**任务无关**，避免对已知六题过拟合。

不涉及"加时长 / 加 token"的做法，因为 R10–R13 已经证明放大预算并不解决真正的问题。

---

## 一、绑定被测字节 = 发布字节（P0，任务无关）

**问题**：R13 中 S1 开发者对同一发布源码做了 135 次浏览器调用；S2 QA 的 6 次浏览器调用全部跑的是审核者自己改过的私有 `dashboard.js`，与候选包字节不一致，最后语法错误不能归给原字节候选。

**改在哪里**：`backend/tools.py` 中 `code.test` 的 `browser` 分支，以及 `backend/browser_spec.py` 的参数校验。

**怎么改**：
1. 发布候选包后，把候选包内每个文件的 `path → sha256` 作为该任务修订的"发布清单"写入账本。
2. `code.test action=browser` 执行前，对 `resources[*]` 和 `path` 的实际 SHA 与"发布清单"逐项比对。
3. 若有任何文件哈希不匹配，默认拒绝执行并返回明确反馈 `{"error":"testing_private_bytes","diff":[...]}`。
4. 需要测试私有改动时，Agent 必须显式写 `"allowPrivateBytes": true`；该次测试只写入 Agent 自己的调试记录，**不计入独立验收**，报告里标记 `coverageType="private"`。

**验收标准**：
- 跑一轮伪造数据：把发布包里的 `app.js` 改一个字节，调用 `code.test` 必须返回 `testing_private_bytes`。
- R13 的 S2 回放中，QA 的 6 次调用应全部被标为 `private`，不会再进入"通过项"计数。

## 二、Planner 给子任务下软时间预算（P0，任务无关）

**问题**：R13 S1 开发者在 44.86 分钟里到第 43.2 分钟才发布候选，QA 只剩约 1 分钟，无实际浏览器调用。当前阶段检查点 `expectedHandoffBy` 是按运行时长平均切片，不考虑子任务复杂度，所以总被模型忽略。

**改在哪里**：`backend/engine.py` 的 Planner 输出校验；`backend/stage_control.py` 的检查点分配。

**怎么改**：
1. Planner 输出 schema 新增每个子任务的时间字段（三项都是**软目标，不是硬杀**）：
   ```json
   {
     "taskId": "qa-s1",
     "estimatedMinutes": 8,
     "minMinutes": 3,
     "maxMinutes": 15
   }
   ```
2. `stage_control.py` 把 `expectedHandoffBy` 改成按 `estimatedMinutes` 加权分配，而不是运行时长平均切片。
3. 子任务运行超过 `maxMinutes` 时，调度优先级下调（让尚未开始的子任务先跑），不强制终止正在执行的子任务。
4. 剩余运行时间低于本子任务 `minMinutes` 时，调度优先级抬升。
5. 运行结束后 `summary.md` 自动输出 `estimated vs actual` 对照表。

**验收标准**：
- 一次真实运行中，所有子任务输出都带有 `estimatedMinutes`，并与实际耗时成对记录。
- 回放 R13 S1 事件流，Executor 超过自估 `maxMinutes` 后，QA 的调度优先级应已抬升。

## 三、交接硬门限：保证下游角色有执行窗口（P0，任务无关）

**问题**：R13 软件题 Executor 吃掉 90%+ 时间，QA/Reviewer 无时间执行。软件题重复测试浪费最明显。

**改在哪里**：`backend/engine.py` 的阶段调度。

**怎么改**：
1. 新增配置 `HANDOFF_HARD_RATIO=0.7`（默认 70%），按剩余墙钟比例计算，不依赖绝对值。
2. 到达运行墙钟的 70% 时，若 Executor 尚未发布任何候选包，强制进入"收尾锁定"：
   - 仅允许 `publish_artifacts`、`package_delivery`、`final`。
   - 拒绝 `code.run`、新增 `code.test`、新增 `web.fetch`、新增 `web.search`。
3. 到达 85% 时，无论是否发布，Executor 让出剩余时间给下游角色（QA / Reviewer）；下游调度优先级抬升到最高。
4. 若 Executor 第一次发布候选早于 70%，不触发锁定（正常路径）。

**验收标准**：
- 回放 R13 S1 事件流，在 70% 墙钟点触发锁定，Executor 后续浏览器调用应被拒绝。
- 新一轮真实运行中，下游角色真正执行动作的题目占比 ≥ 5/6。

## 四、返工版本门禁（P0，任务无关）

**问题**：R13 N2 审核者已读取新版，仍引用旧 artifact 和旧措辞再次返工，触发上限并跳过后续包装。

**改在哪里**：`backend/engine.py` 的 `review` 动作处理，`backend/contracts.py` 的审查输入校验。

**怎么改**：
1. `review` 动作 JSON 必须带 `reviewedArtifactIds: [...]` 与 `reviewedHashes: {...}`。
2. 执行前比对：若 `reviewedHashes` 中任何 artifact 的 SHA 与 producer 当前最新版本不一致，先返回一次差异反馈，拒绝执行：
   ```json
   {"error":"review_against_stale_version",
    "latest":{"artifactId":"...","sha":"..."},
    "reviewed":{"artifactId":"...","sha":"..."}}
   ```
3. 同一返工上限内只提醒一次。Agent 仍坚持旧版返工时，自动降级为 `partial`，不再触发新一轮返工循环。

**验收标准**：
- 回放 N2 事件，第二次旧版返工请求应被门禁拦截。
- 新增单元测试：producer 发布 v2 后，review 请求 v1 应被拒绝。

## 五、包装 / 验收闭环（P0，任务无关）

**问题**：R13 F2 全部子任务 done、总体仍 partial —— 因为 README 与交付说明是打包后新增的，没有匹配的最终审查。

**改在哪里**：`backend/delivery.py` 的 `package_delivery` 成功回调。

**怎么改**：
1. 打包成功时，计算包内每个文件与"该文件最近一次 review_pass 事件所覆盖的 SHA"的差异：
   - 完全一致 → 复用既有审查证据，标 `coverageSource="inherited"`。
   - 字节有变化或无历史审查 → 列入 `uncoveredFiles[]`。
2. 若 `uncoveredFiles` 非空，自动生成一个最小审查微任务：仅审"差异文件"，不重复整包。
3. 全部覆盖 → 整体允许标 done；仍有未覆盖 → 保持 partial，并明确给出缺口清单。

**验收标准**：
- F2 回放：新增 README 后应自动生成针对 README 的 review 微任务。
- 新增测试：打包前后字节不变的审查记录可直接继承，不重复触发微任务。

## 六、验收点动态抽取（P0，任务无关）

**问题**：原先的"场景差异化清单"是按已知 S1/S2/N1/N2/F1/F2 预写，期末换新题目全部失效。模型自己判断又容易漏项（F1 用长期国债率解释短期现金收益、F2 手机横向溢出、N1 字数偏短）。

**改在哪里**：`backend/engine.py` 规划入口新增"验收点抽取"步骤；`backend/contracts.py` 新增 `extracted_acceptance_checks` 字段。

**怎么改**：
1. 用户任务下达后，Planner 用一次模型调用，根据**任务原文**抽取 3–6 条**可机器核验**的验收点，写入 `acceptance_checks[]`。Schema 示例：
   ```json
   {
     "id": "ac1",
     "description": "交付包必须能在浏览器中打开并显示主界面",
     "verifiable_by": "browser_check|file_exists|word_count|number_sum|cross_doc_consistency",
     "params": {...}
   }
   ```
2. 支持的核验器从通用维度出发，**不写死题目场景**：
   - `file_exists`：指定扩展名/数量的文件存在。
   - `browser_check`：HTML 能打开，没有 console error。
   - `word_count`：文本长度在用户给出或任务暗示的区间内。
   - `number_sum`：若任务涉及金额/百分比，合计等于目标。
   - `cross_doc_consistency`：跨文件引用的关键值一致。
3. 这些验收点在候选包生成后自动跑；失败项进入返工反馈。
4. Planner 抽取时同时必须记录 `extraction_source`（来自用户哪段话），便于审计。

**验收标准**：
- 用一道全新编造的任务（例如"做一个卡路里追踪 web 应用"）试跑，Planner 能抽出至少 3 条验收点。
- 回放 R13 F1，抽取出的验收点中应包含"权重合计 = 100%"。

## 七、评测指标自动化（P1，任务无关）

**问题**：课程 `requirements.md` 第 3 节要求 harness **自动追踪并报告** "任务完成率、执行时间"。当前 `mid-test-r13-20261116.json` 字段散落、README 需要人工总结。

**改在哪里**：`benchmarks/mid_test_live.py` 的输出处理。

**怎么改**：
1. 每题结束后生成固定 schema：
   ```json
   {
     "task": "<task-id>",
     "overall_status": "done|partial|failed",
     "subtask_completion_rate": 0.83,
     "wall_time_seconds": 2690,
     "model_calls": 97,
     "reported_tokens": 1407104,
     "unknown_usage_calls": 9,
     "delegation_events": 2,
     "memory_hits": 0,
     "formal_package": true,
     "candidate_package": true,
     "acceptance_checks": {"passed": 16, "failed": 1, "unassessed": 0},
     "failure_modes": ["version_mismatch", "handoff_too_late"]
   }
   ```
2. 全部题跑完后自动汇总成一张 Markdown 表格写入 `--output` 目录的 `summary.md`。
3. `failure_modes` 使用预定义枚举（见第八条），不要自由文本。

**验收标准**：
- 跑一次任务，`summary.md` 直接可作为最终报告 4.3 节的原始表格。
- 所有字段都能从账本算出，不依赖人工解读。

## 八、失败模式分类枚举（P1，任务无关）

**问题**：历轮报告的失败原因散落在正文，不利于 4.3"失败模式讨论"。

**改在哪里**：新建 `backend/failure_modes.py`。

**怎么改**：定义枚举：

| 枚举值 | 含义 |
| --- | --- |
| `version_mismatch` | 审查 / 测试对不上当前发布版本 |
| `private_bytes_tested` | 测试的是私有改动不是发布字节 |
| `handoff_too_late` | 开发者耗时过多，下游角色无时间 |
| `repeated_action_loop` | 重复动作被兜底停止 |
| `source_not_read` | 声称核查但无真实 `file.read` / `web.fetch` |
| `metric_unit_error` | 单位 / 分母 / 期限错用 |
| `budget_exhausted` | Token / 调用 / 时间预算耗尽 |
| `model_request_failed` | 上游模型请求超时或错误 |
| `storage_reliability_bug` | 存储读写失败处理不当 |
| `preference_ignored` | 忽略用户已表达偏好 |
| `acceptance_check_failed` | 动态抽取的验收点未通过 |

每类在 `backend/engine.py` 或各工具处检测时打标签，直接进 `failure_modes[]`。

**验收标准**：
- R13 事件流回放能够把每题失败全部归入一个或多个枚举。
- 新一轮 run 生成的 `summary.md` 可按枚举汇总出条形图数据。

## 九、动态任务委派的证据化（P1，任务无关）

**问题**：R13 动态委派事件 = 0。课程 2.1 "自主任务委派"没有可展示证据。只有 Planner 的初始分工不算运行时委派。

**改在哪里**：`backend/engine.py` 的子任务创建路径。

**怎么改**：
1. 区分两类子任务：
   - `origin="planner"`：初始规划生成。
   - `origin="runtime_delegation"`：Agent 在执行中通过 `delegate` 动作新建。
2. 规划提示明确鼓励在遇到"需要另一专业能力"时使用 `delegate`，例如研究员发现数学不确定时委派给 QA 做核算。
3. `summary.md` 中单独列 `delegation_events`；无则在报告中如实记为 0。

**验收标准**：
- 至少一道题出现 `origin="runtime_delegation"` 的事件记录。
- 事件包括：发起者、受派者、子任务、理由、结果回传。

## 十、记忆开关的 A/B 对照（P1，任务无关）

**问题**：R13 已确认记忆命中 0，24 次候选 21 unassessed。无法证明"记忆进化改善了性能"。

**改在哪里**：`benchmarks/mid_test_live.py` 增加 `--memory` 开关；`backend/memory.py` 支持运行级禁用。

**怎么改**：
1. `--memory on|off|readonly` 三档：
   - `on`：正常读写与自动确认。
   - `off`：完全禁用记忆检索与写入。
   - `readonly`：只读既有确认策略，不写新记忆。
2. 固定同一题、同模型、同额度，对比 `memory=on` 和 `memory=off` 各跑 ≥ 3 次，比较完成率 / 耗时 / 失败模式。
3. 结果写入 `benchmarks/reports/memory-ablation-*.json`，附在最终报告。

**验收标准**：
- 产出一张对照表：相同任务、相同模型、相同预算下，两档各 3 次运行的指标对比。
- 若对照无差异，报告中如实写"未证明收益"，不虚构结论。

## 十二、用户偏好跨任务继承（P1，任务无关）

**问题**：S2 默认 14 天，忽略了之前 S1 用户表达的"7/30/90 天"偏好；N1 字数低于用户"约 800 词"偏好。偏好只能靠 Agent 记忆碰运气。

**改在哪里**：新增 `backend/team_preferences.py`（运行作用域，与 Agent 私有记忆不同）；`backend/engine.py` 的 Planner 上下文注入。

**怎么改**：
1. 定义偏好 Schema：`word_count_range`、`date_range_shortcuts`、`tone`、`language`、`decimal_places` 等。这些**不是场景清单**，是跨任务通用的参数类型。
2. 每次用户在群聊中的回答进入 pipeline 时，用一个轻量抽取步骤把显式偏好写入 `team_preferences.json`。
3. Task 2 规划时，把本团队 `team_preferences` 作为高优先级上下文注入 Planner 与所有 Agent 的初始化提示。
4. 偏好冲突（用户改口）时保留最新一次，旧偏好归档，不删除。

**验收标准**：
- 跑一次 Task 1 → Task 2：Task 1 中用户说"约 800 词"，Task 2 规划提示里能看到该偏好。
- 偏好写入事件在报告里可追溯。

## 十三、并行度最大化（P1，任务无关）

**问题**：当前单题内部四角色的调度在时间紧张时未充分并行。Research 和 Executor 的早期阶段其实可以重叠。

**改在哪里**：`backend/engine.py` 的 DAG 调度器。

**怎么改**：
1. 规划阶段鼓励 Planner 显式标出"可并行子任务"；调度器默认并行，而不是等待前一任务完全完成。
2. 对独立 I/O 工具调用（`web.fetch`、`file.read`）允许同一 Agent 内并发。
3. 日志中记录"并行节约时间"，写入 `summary.md`。

**验收标准**：
- R13 回放中，Research 的前期 `web.fetch` 与 Executor 的脚手架搭建应能并行执行。
- 相同任务对比，并行开启前后总耗时差异 > 10% 即算有效。
