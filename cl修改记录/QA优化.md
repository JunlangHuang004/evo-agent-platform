# Q&A 优化记录

本文档记录对现有改进方案的追问与进一步定位，避免把精力误放在"看起来慢"但其实不是瓶颈的地方。

---

## Q1：是不是这些任务主要耗时在 QA，开发时间不多？能不能精简？

### A：数据恰好相反——瓶颈在 Dev 的冗余自测，QA 几乎没时间跑

R13 里最典型的两个例子：

| 指标 | S1 | S2 |
|---|---|---|
| Dev 浏览器调用 | **135 次**（108 成功） | 若干 |
| QA 浏览器调用 | **0 次** | 6 次（且测的全是审核者私有改动） |
| Dev 首次发布候选时间 | 4.48 分钟 | — |
| Dev 发布后仍做的浏览器调用 | **~130 次** | — |
| QA 实际执行窗口 | ~1 分钟 | 几乎为 0 |

读懂这组数据：

1. **Dev 4.5 分钟就发布了候选包**，"做出来"并不慢。
2. 剩下约 40 分钟 Dev 都在**重复测自己的代码**，不是在改 bug——是对相同字节重复跑同类浏览器测试。
3. QA 接棒时墙钟已经到 44 分钟，根本来不及。
4. S2 的 QA 虽然跑了 6 次，但全测在自己改过的私有 `dashboard.js` 上，与发布包字节不一致——既浪费了时间，又不能算作独立验收。

**结论**：真正该精简的**不是 QA，而是 Dev 的冗余自测 + QA 的错版本测试**。QA 本身不能动，课程 2.2 "验证"和 4.3 "失败模式"都需要 QA 的独立证据，砍 QA 会直接丢失评分证据。

## 可直接落地的精简（与现有 `改进.md` 咬合）

### 1. 发布后禁止 Dev 对同字节重测

**改在哪里**：`backend/engine.py` 的 Dev 动作处理路径。

**怎么改**：Dev 一旦 `publish_artifacts`，之后只有在**新字节写入**后才允许再次对自己发布过的文件做 `code.test`。没有字节改动就想再跑同一类 browser check → 直接拒绝，反馈"发布后 Dev 的同字节自测无新证据价值，请交接"。

**预期**：S1 Dev 的 135 次调用压到 ≤ 20 次。

---

### 2. 同字节 × 同测试规格去重缓存

**改在哪里**：`backend/tools.py` 的 `code.test browser` 分支。

**怎么改**：增加缓存键 `(entry_sha, resources_sha_map, checks_hash)`。相同键命中时直接返回上次回执，不实际启 Docker。配合第 1 点强制 Dev 换新字节才能跑新测试。

**注意**：这节省的是 Dev 自测的后期重复，不影响 QA 首测（QA 用的 agent 和缓存命名空间独立，首次命中失败——因为 QA 从未对该 SHA 发起过测试）。

---

### 3. 发布即交接，默认启动 QA

**改在哪里**：`backend/engine.py` 的 DAG 调度器。

**怎么改**：
- Dev 完成 `publish_artifacts` 后，调度器**立即**把 QA 任务置为 `ready`，不再等待 Dev 的"自检收尾"。
- Dev 后续的测试请求降级为"调试记录"，不写入账本的 `testedFiles`，也不计入独立验收覆盖。

**配合**：与 `改进.md` 第一条（发布字节绑定）和第二条（软时间预算）组合生效。

---

### 4. QA 测试窗口下限

**改在哪里**：交付契约 schema；`backend/engine.py` 调度门限。

**怎么改**：在交付契约里新增 `qaBudget.minimumMinutes`（软值，由 Planner 估）。Dev 时间超支到 QA 的 `minimumMinutes` 之内时，自动触发现有的"交接硬门限"（70% / 85%），不等 Dev 自觉。

---

## 写入 `改进.md` 的建议位置

建议把以上 1–3 作为一条新增 P0 放在**现有第一条（字节绑定）和第二条（软时间预算）之间**，命名"二-A. 禁止 Dev 对同字节冗余自测"。第 4 条可以直接合并进现有第三条（交接硬门限）的"怎么改"小节。

草稿：

> **二-A. 禁止 Dev 对同字节冗余自测（P0，任务无关）**  
> 问题：R13 S1 Dev 135 次浏览器调用中约 130 次是发布后对同字节的重测，QA 因此只剩 1 分钟。  
> 改法：`code.test` 增加 `(文件 SHA, 测试规格 SHA)` 缓存键；Dev 发布后对同字节的 `code.test` 直接返回缓存并提示交接，不再占用墙钟。  
> 验收：R13 S1 回放，Dev 调用数应压到 ≤ 20；S2 QA 对发布字节的调用数 ≥ Dev 调用数。

## 不要做的事

- **不要精简 QA 的测试步数或覆盖范围**。QA 的独立验收证据是课程必考项，R13 恰恰是 QA 太少不是太多。
- **不要给 QA 加新的"快速通道"去跳过某些检查**。快速通道的产物无法作为"失败模式分析"的证据。
- **不要对 Dev 做硬杀**。只做"去重 + 调度抢占"，让 Dev 的冗余动作变成空操作，而不是中断可能正在修 bug 的动作。
