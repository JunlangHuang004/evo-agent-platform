# 记忆模块：课程要求、当前实现与改进方案

## 1. 老师的要求

`requirements.md` 第 2.2 节原文：

> **记忆与演进：** 每个智能体都必须拥有独立的记忆机制，例如使用向量数据库或本地 JSON 日志。智能体必须能够**从过去任务执行的成功与失败经验中学习**，以提升后续任务的表现。

第 4.3 节还要求在最终报告里讨论：

> **失败模式和测试过程中智能体记忆演变情况**

拆成可考核的点：

| 要求 | 细节 |
|---|---|
| **R1 独立性** | 每个 agent 有自己的记忆，互不混用 |
| **R2 持久化** | 向量库 / JSON / 其他持久存储都行 |
| **R3 从经验学习** | 成功 ✅ 和失败 ❌ 都要能进入记忆 |
| **R4 提升后续表现** | 记忆不能只是归档，要真的在后续任务里影响决策 |
| **R5 演进可观测** | 报告里要能看到"记忆从 T1 到 T2 的变化" |

**老师没有要求的**（避免过度工程）：

- 不要求复杂 embedding / 向量检索（原文"向量数据库或本地 JSON 日志"任选）。
- 不要求跨团队共享。
- 不要求"记忆能自动决定派哪个 agent"。

## 2. 当前实现

### 存储层（`backend/persistence.py`）

- SQLite 表 `memories (id, owner, payload)`，`owner` = `agent_id`。
- `add_memory` / `memories(agent_id)` 等按 owner 隔离。
- 启动时整表加载，持久化没问题。

### 记忆类型（`backend/memory.py`）

分四种 `kind`：

| kind | 内容 | 产生时机 |
|---|---|---|
| `episodic` | 单次任务执行的真实事实（run_id, task_id, success, reason, call_ids） | 任务结束时自动写 |
| `procedural` | 可复用的"做法"（lesson + trigger + conditions + evidence） | Agent 在 reflection 里 propose |
| `semantic` | 通用知识 | 同上 |
| `working` | 临时上下文 | 任务内部，不进 SQLite 的持久内存 |

### 学习闭环（`backend/learning.py`）

- `observe_failure` → 失败时自动把真实错误、工具调用、失败原因写成 episodic 记忆。
- `context(agent_id, query)` → 任务开始时按查询词检索 top-k 记忆（BM25F 算法）注入 `action_prompt`。
- `begin_trial` / `settle_trial` → 记录某个 procedural 记忆**是否在本次任务里被真实采用**，用 agent 的 `reflection.trialMemoryIds` 核对。
- **确认机制**：候选 procedural 记忆默认不可检索，必须经人工（UI 的"Agents 与记忆"里点确认）或独立 QA 的证据验证后才上线。

### 调度 / UI 层

- `snapshot()` 中 `state['learnedMemories'] = {agent: self.memory.list(agent) for agent in self.agents}` —— 每个 agent 的记忆对应一个面板。
- 前端 `memory_confirm` 和 `memory_share` 两个动作显式确认或共享。
- 任务输出里 `reflection.trialMemoryIds` 由模型填写，告诉系统"我采用了这几条"。

### 与老师要求对照

| 要求 | 现状 | 判定 |
|---|---|---|
| R1 独立性 | SQLite owner 列 + 按 agent 查询 | ✅ |
| R2 持久化 | SQLite `.runtime/<team>/platform.db` 的 memories 表 | ✅ |
| R3 成功+失败学习 | 失败自动走 `observe_failure`；成功靠 `reflection.trialMemoryIds` + `settle_trial` 回写置信度；但**纯成功不会自动写新经验**，需要 agent 主动 `propose` | ⚠️ 半达成 |
| R4 影响后续决策 | context 注入 action_prompt，带 trial id 让模型显式采用 | ✅ 技术上可，但 R10–R13 实测**命中 0** |
| R5 演进可观测 | 面板能看到 memories 列表，snapshot 有 memoryHits | ✅ 能展示 |

## 3. 两个真正的差距

### 问题 1：R10–R13 实测，长期学习命中 0

六题实测里：

- **已确认记忆检索命中 0 次**。模型在新任务规划时，没真的"因为想起之前 S1 的错误而避免"。
- **24 次候选记忆试验里 21 次 `unassessed`** —— 写入后没人（人或系统）去确认它们是否真的有用。
- 结果：记忆写了一堆（episodic 全自动写入），但没人读。

这是**最大的差距**：机制齐全，闭环没跑通。

### 问题 2：没有对照实验

老师 4.3 要求"记忆演变的讨论" —— 你需要证明"用记忆 vs 不用记忆，后者表现更差"。目前没做过这个 A/B。R13 报告里是诚实写的：

> 已确认策略命中为零，19 次候选试验均未获有效评估；因此尚不能宣称长期学习已改善真实产品交付。

## 4. 改进方案（三层）

### 轻度（必做，1–2 小时）

让现有机制别白写：

1. **成功任务也自动 propose 候选记忆**
   当前只有失败自动入，成功要靠 agent 自觉 propose。改成任务 `done` 时也触发一次 helper —— 把成功的 `call_ids` + `outputContract` 写成一条候选 procedural 记忆，title 带任务类型。这样成功经验也会入库。

2. **自动确认一批"低风险模式"**
   当前确认必须人工点。加一条规则：**同类任务连续成功 2 次，且证据链完整（browser pass + review pass）→ 自动把候选升为 confirmed；失败 1 次又降回候选。**

3. **在 `planning_prompt` 里显示"以前这类任务的 top-3 相关经验"**
   目前 `context()` 已经在 `action_prompt` 里注入，但 **Planner 的系统提示没拿到**。让 Planner 规划时能看到"S1 之前的类似任务，Dev 花了太长时间导致 QA 没时间" —— Planner 可能会主动把 handoff 卡在前期。

### 中度（强烈推荐，3–5 小时）

做一次能写进报告的记忆对照实验：

4. **在 `benchmarks/mid_test_live.py` 增加 `--memory on|off|readonly` 开关**（改进.md 第十条已提过）。
5. **固定同一题、同模型、同额度**，`memory=on` 和 `memory=off` 各跑 3 次，比较完成率 / 耗时 / 失败模式。
6. **输出 `benchmarks/reports/memory-ablation-*.json`**，直接作为 4.3 报告的证据。

这是最有价值的改动：**从"我们有记忆"升级成"我们证明了记忆影响表现"**。

### 重度（不推荐，10+ 小时）

换向量检索或语义聚类。**不推荐的理由**：

- 老师原文明说"向量数据库或本地 JSON 日志"，JSON + BM25F 已经达标。
- R13 命中 0 的根因不是"检索精度不够"，是"任务规划阶段不读记忆"。换 embedding 也解决不了闭环断裂。
- 增加依赖、Docker 体积、调试时间 —— 都是展示风险。

---

## 5. 建议执行顺序

**做"轻度 + 中度"的组合**，总共 5–7 小时：

- 轻度 1 和 2 让记忆真的有东西并能自动确认（解决 R13 命中 0 的问题）。
- 轻度 3 让 Planner 也看到记忆（评分看重的"路由基于记忆"）。
- 中度 4–6 做对照实验（评分看重的"4.3 讨论"）。

**顺序**：

1. **轻度 1**（成功任务也 propose 候选）—— 15 分钟就能加，立刻提升记忆池规模。
2. **轻度 2**（自动确认低风险模式）—— 30 分钟，让闭环闭合。
3. **轻度 3**（Planner 能看到相关经验）—— 1 小时。
4. **中度 4–6**（A/B 开关 + 跑一次对照）—— 2–3 小时代码 + 实际跑一次取数据。

这些改动都不触碰课程要求的工具权限、沙箱、协作拓扑约束，全是 **`memory.py` / `learning.py` / `engine.py` 的本地增强**，风险可控。
